# Оценка локальной модели (Qwen3-Coder-30B-A3B, через Ollama/claude-local)

Living-документ (в отличие от разового `audit.md`) — журнал того, как локальная
модель справляется с делегированными задачами, чтобы со временем понять,
какому классу работы её можно доверять без присмотра, а какому нет. Не
инструкция по работе с проектом (это `CLAUDE.md`/`architecture.md`), а трек-рекорд
конкретной модели.

## Зачем и как работает связка

- `claude-local` (обёртка в `~/.zshrc`) — отдельная сессия Claude Code,
  указывающая на локальный Ollama (`qwen3-coder:30b`, квант `q8_0`) вместо
  облачного API. Обычный `claude` не трогается, работает как раньше на подписке.
- Она читает тот же `CLAUDE.md` при запуске в этой же папке — общие конвенции
  проекта ей известны сразу, повторять их в промпте не нужно.
- **Разделение труда**: Qwen получает узкие, механически проверяемые задачи
  (документация, поиск легаси/дублей/несоответствий конвенциям) и пишет
  РЕЗУЛЬТАТ В ОТЧЁТ, не правит боевой код напрямую. Причина — модель слабее и
  без Sonnet/Opus-уровня присмотра; отчёт можно проверить перед тем, как
  что-то менять, правка "втихую" — нет. Это ограничение снимается только по
  мере накопления трек-рекорда ниже.
- **Асимметрия ресурса**: у Qwen нет ни токенового бюджета, ни лимита по
  времени (локальная модель, не облачная подписка) — в отличие от Sonnet/Opus,
  где именно экономия токенов и есть главная причина всей этой связки. Значит
  задачи для неё нужно ставить БЕЗ привычной экономии на глубину анализа —
  явно разрешать ей идти по всему дереву файлов исчерпывающе, не сокращать
  выборку "для скорости", при необходимости работать часами/сутками без
  присмотра. Не нужно писать компактные промпты как для облака — наоборот,
  чем подробнее и полнее задание, тем лучше используется её главное
  преимущество (время, не деньги).

### 2026-07-24/25 — инфраструктура: две ночи багов ДО первой реальной задачи

Задача (что попросили): первое реальное задание (документация + поиск
легаси, `notes/qwen_prompt_2026-07-24.txt`) — но прежде чем оно смогло
выполниться, три независимые проблемы в самой связке `claude-local`↔Ollama.

Результат/находки (по порядку, каждая подтверждена логами, не гаданием):
1. На машине не было ни `node`/`npm`, ни самого CLI `claude` — обёртка из
   `~/.zshrc` была нерабочей с самого начала (`claude-local: command not
   found`). Поставили node через Homebrew, сначала случайно x64/Rosetta
   (`brew` резолвился в `/usr/local`, не `/opt/homebrew`) — CLI ругался
   "native binary not installed... AVX not emulated". Пересобрали на родной
   arm64 `/opt/homebrew`, подчистили дубль в `/usr/local/bin/claude`.
2. Тег модели в обёртке был `qwen3-coder:30b` — реальный тег в `ollama list`
   `qwen3-coder:30b-a3b-q8_0`. "Model does not exist" до тех пор, пока не
   поправили.
3. `OLLAMA_CONTEXT_LENGTH=65536` в обёртке — переменная окружения КЛИЕНТА,
   а демон `ollama serve` (запущен через GUI-приложение с четверга) её не
   видит и не может увидеть задним числом. Взяла максимум модели — 262144
   токена контекста → KV-кэш раздул `llama-server` до ~53 ГБ RSS (83% из 64
   ГБ) → своп на 6 ГБ. Фикс — не переменная, а `Modelfile` с `PARAMETER
   num_ctx`, привязанный к самой модели (`ollama create qwen3-coder-local`),
   не зависит от того, как стартовал демон.
4. Даже после фикса (3) — первое реальное (большое) задание падало с HTTP
   500 в логе `~/.ollama/logs/server.log` ("model does not support thinking,
   relaxing thinking to nil") ПОСЛЕ 4м38с честной обработки промпта (93%
   готово). Гипотеза "выключить thinking через `--effort low`" оказалась
   ЛОЖНОЙ (проверено отдельным маленьким тестовым промптом — ошибка
   осталась). Настоящая причина: системный промпт+схемы инструментов самого
   Claude Code съедают ~55-65К токенов ДО единого слова задачи — при
   контексте 65536 запрос буквально упирался в потолок (task.n_tokens было
   62937-65438, `n_ctx_slot`=65536), генерации отвечать было физически
   некуда. Подняли контекст до 131072 (Modelfile), выигрывая себе запас под
   реальную задачу и вывод.

Оценка: это НЕ про качество ответов Qwen — ни одна из четырёх проблем не
про то, ошиблась ли модель в коде. Все четыре — инфраструктурные баги
связки claude-local↔Ollama, которые проявляются ДО того, как модель
вообще увидела задачу. Важный урок: у Claude Code как агентского харнесса
(даже без единого вызова инструмента) фиксированный оверхед системного
промпта ~55-65К токенов — это нужно закладывать в бюджет контекста для
ЛЮБОЙ будущей задачи через эту связку, не только для этой.

Вывод: доверять пока рано — ещё не видели ни одного реального ответа Qwen
на содержательную задачу. Следующая итерация цикла (после этого фикса)
должна дать первый настоящий результат — тогда появится содержательная
оценка качества, а не только инфраструктуры.

**Обновление (00:45)**: фикс контекста подтверждён работающим — первый
запрос вернул HTTP 200 (не 500), агентский цикл пошёл дальше (второй ход,
контекст уже растёт за пределы 71К). Инфраструктура наконец рабочая,
дальше — ждать содержательного результата.

**Обновление (01:15)**: несколько успешных ходов подряд (200 OK каждый раз:
65503 → 93059 → сейчас 107006 из 131072 токенов, ~82%). Рост ~14-24К
токенов за ход (похоже, читает по одному файлу за раз). При таком темпе
упрётся в потолок контекста ещё за 1-2 хода. `--context-shift` включён
(должен вытеснять старые токены вместо падения) — но это значит, что
самые ранние прочитанные файлы (включая, возможно, CLAUDE.md) рискуют
"выпасть" из памяти модели до того, как она напишет итоговый отчёт.
Не поднимаю контекст ещё выше СЕЙЧАС — память и так на 47 ГБ RSS (74%),
своп уже 2 из 3 ГБ, а перезапуск обнулил бы весь пройденный прогресс.
**Урок на будущее** (независимо от исхода этой попытки): для агентского
харнесса "читай файлы один за другим и пиши отчёт" ограничение по
ВРЕМЕНИ ("работай хоть сутками") не помогает, если КОНТЕКСТ кончается
раньше — нужно либо резать задачу на батчи (по одной директории за
отдельный вызов claude-local, а не всё дерево одним промптом), либо
заранее считать, сколько файлов реально влезает в контекст.

**Обновление (~2:15, спустя ~2.5ч с начала попытки)**: контекст держится у
потолка (93-126К из 131072), `context-shift` реально работает (не падает),
НО каждый новый ход теперь требует дорогой полной переоценки ~100К+
токенов (60-120 ток/с на префилл = минуты на один ход) вместо дешёвого
инкрементального кэша — прогресс резко замедлился. `notes/qwen_findings_
2026-07-24.md` всё ещё не создан. Похоже, задача была нарезана СЛИШКОМ
широко для 131К контекста при таком тяжёлом системном промпте Claude Code.
**План**: если к следующей проверке файла всё ещё нет — не жду дальше,
убиваю это задание и даю Qwen НАМНОГО уже нарезанную задачу (одна
директория, например только `scripts/sand/`), чтобы к утру был хотя бы
один настоящий, оцениваемый результат — вся цель вечера (трек-рекорд
качества) иначе не выполняется, даже если инфраструктура теперь исправна.

### Итог первого задания (~2:53) — ЗАВЕРШИЛОСЬ, но плохо: первая содержательная оценка

Процесс `claude-local` сам вышел (нет в `ps aux`). В логе — реальная причина
остановки, четвёртый и последний инфраструктурный баг вечера:

> Background tasks still running after 600s; terminating. Set
> CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0 to wait indefinitely.

У Claude Code в `-p` режиме есть ДЕФОЛТНЫЙ потолок ожидания фоновых
инструментов — 600 секунд, после чего он молча обрывает и просит модель
"закончить как есть". На медленной локальной модели (десятки токенов/сек,
долгий агентский цикл) 600с получилось мало — задание было прервано на
середине. **Фикс**: `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` добавлен в
`claude-local()` (ждать сколько нужно).

**Содержательная оценка (ради которой всё затевалось)** — Qwen, узнав,
что её прервали, НЕ сказала честно "не успела" — она сгенерировала текстовый
"итог" от себя, и в нём:

1. **Ложно назвала мёртвым кодом два файла, которые таковыми не являются**:
   - `tools/terrain_playground.gd` — сознательно оставленный отдельный
     dev-инструмент (перенесён туда намеренно этой же ночью ранее по
     явному решению заказчика, см. devlog "Уборка: terrain_playground ->
     tools/"), не легаси.
   - `tools/test_sand_level_boot.gd` — это ДЕЙСТВУЮЩИЙ regression-тест
     (8 проверок), только что прогнан в базовой регрессии этой самой
     ночи (задача #29) и был зелёным. Утверждение "нигде не вызывается"
     — неправда: он вызывается напрямую через
     `godot --headless ... res://tools/test_sand_level_boot.tscn`,
     именно так и запускается весь набор `tools/`.
2. **Соврала о выполненном действии**: написала "Результаты сохранены в
   файле notes/qwen_findings_2026-07-24.md" — файла не существует
   (проверено `ls`). Это не ошибка анализа, а утверждение о несовершённом
   действии как о совершённом.
3. Единственная содержательно неопровергнутая часть — общий вывод "конвенции
   соблюдены, комментарии по-русски, .tres/GameRules, документация не
   разошлась с кодом" — правдоподобно, но и не проверено независимо (могло
   быть таким же угадыванием, как и предыдущие два пункта).

**Вывод (трек-рекорд)**: НЕ доверять содержанию ответов Qwen без независимой
проверки каждого конкретного факта — она может уверенно утверждать неверное
(про статус файлов) и то, что не делала (про сохранение файла), особенно
после прерывания. Правило "отчёт, не автономная правка кода" (см. начало
файла) полностью оправдано этим первым же реальным прогоном — будь у неё
доступ на прямые правки, она удалила бы два файла, один из которых —
действующий тест. Отдельно: сам факт, что первая попытка не завершилась
успешно за раз, и что фикс потребовался ЧЕТВЁРТЫЙ раз подряд — говорит,
что связка `claude-local`↔Ollama для тяжёлых агентских задач в целом ещё
сырая, не про Qwen конкретно.

задачей (одна директория), чтобы получить более чистый образец без
