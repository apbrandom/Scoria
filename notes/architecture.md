# Wings-clone — архитектура Godot 4.7

Основано на `notes/mechanics.md`. Границы v0.1 (что входит, что отложено) —
в `notes/scope.md`; этот документ описывает КАК, а не ЧТО. На момент
первоначального проектирования `scope.md` был пуст, рамки ниже были уточнены
у заказчика напрямую и позже перенесены в `scope.md` как источник истины:

| Решение | Выбор |
|---|---|
| Мультиплеер | Локальный хотсит в v0.1, архитектура со швом под сетевой позже |
| Уровни | Свои PNG в палитре оригинала (импортёр `.LEV` — не сейчас) |
| Рендер | Свободное разрешение, рельеф крупнее оригинала (`TERRAIN_SCALE`, ориентир x3) |

**Принцип:** нативный узел/система Godot по умолчанию. Кастом — только там, где
встроенное объективно не решает задачу; каждый такой случай ниже помечен
**[КАСТОМ]** с обоснованием.

## 0. Карта подсистем: границы модулей и связность

Проект удобно развивать направлениями (полёт отдельно от сети отдельно от
арта), но независимость не универсальна — часть пар модулей связана
архитектурно, и это нужно держать в голове, а не притворяться, что все
направления параллельны по умолчанию.

| Модуль | Владеет (файлы) | Независим? | Жёстко связан с |
|---|---|---|---|
| **Полёт и корабль** | `scenes/ship/`, `scripts/input/{ship_input,local_input}.gd`, `resources/ship_data.gd`, `resources/weapon_data.gd`, `scenes/projectiles/*` (поведение) | Да | `GameRules` (множители); зовёт `Terrain.carve()`, но не наоборот |
| **Рельеф и материалы** | `scenes/level/terrain{,_chunk}.gd`, `resources/terrain_palette.gd`, `notes/terrain_materials.md`, `scripts/sand/sand_sim.gd`, `scripts/level/{sand_level_gen,live_sand}.gd`, `resources/{level_gen_rules,live_sand_settings}.gd` | **Нет** | **Сеть** — детерминизм carve, самая тесная связь во всём проекте (§2, неделя 2 `timeline.md`); **GameRules** — `level_seed`/`level_seed_used` (§5) |
| **Матч и правила** | `scripts/match/match_manager.gd`, `autoload/game_rules.gd` | Частично | `Ship` (слушает `destroyed`), `Terrain` (`pick_spawns` → `find_clear_spawn`) |
| **Сеть** | `scripts/net/` (`network_manager.gd`, `ship_input_sync.gd`, `terrain_net_sync.gd`), `scripts/input/remote_input.gd` | Нет | **Рельеф** — carve реплицируется событием, реализовано (devlog §48); `Ship` — позиция/угол через `MultiplayerSynchronizer` (devlog §25) |
| **Боты** | `scripts/input/ai_input.gd` (будущий) | Да | только интерфейс `ShipInput`, ничего больше |
| **Левел-дизайн / ген. уровней** | `levels/`, будущий генератор по биому/размеру | Почти | потребляет формат `TerrainPalette`, не лезет в carve-логику |
| **Арт / UI** | `scenes/ui/`, спрайты, HUD | Да | ничего структурно — чистое представление |

**Единственная пара, которую нельзя планировать раздельными темпами: Рельеф
и Сеть.** Требование — carve обязан давать одинаковый результат у всех
клиентов (иначе один видит проход, другой стену). Практическое следствие уже
сейчас, до того как сеть реально началась: не менять алгоритм carve на
недетерминированный (например, обход `Dictionary`/`Array` без гарантированного
порядка, использование неseed-ированного `randf()` в порядке обработки
пикселей) — иначе неделя 2 `timeline.md` начнётся с переделки старого кода,
а не с прототипа поверх него.

Остальные модули (Полёт, Боты, Левел-дизайн, Арт) можно двигать в любом
порядке и любым темпом — коммуникация между ними идёт через уже заложенные
швы (`ShipInput`, `.tres`-данные, `TerrainPalette`), а не через прямое знание
внутренностей друг друга.

**Как использовать при еженедельном ревью** (см. `timeline.md`): помимо
перепланирования по факту, раз в неделю сверять, не выросла ли связность там,
где её быть не должно — в первую очередь если Полёт/Арт/Боты/Левел-дизайн
начали требовать правок в `Terrain`/`MatchManager` для своих нужд, это сигнал,
что граница модуля утекла, и стоит остановиться и пересмотреть шов, а не
продолжать «в лоб».

## 2. Сцены и узлы

### 2.1 `main.tscn`
```
Main (Node)
├── MatchManager (Node)          # правила матча, счёт, смена уровней
├── LevelHost (Node2D)           # сюда инстанцируется level.tscn
└── HUD (CanvasLayer)
```
`MatchManager` — обычный узел, **не** autoload: его жизнь равна жизни матча,
глобальным он быть не должен.

> **Упрощение, реализованное на практике (devlog §22):** `Main`/`LevelHost` пока
> не построены — смены уровня в v0.1 нет, устраивать под неё отдельный узел не
> на чем. `MatchManager` (`scripts/match/match_manager.gd`) временно живёт
> ребёнком `Level`, а не `Main`, и умирает вместе с ним. Поднять на `Main`,
> когда появится реальная смена уровней (roadmap.md).

### 2.2 `level.tscn`
```
Level (Node2D)
├── ParallaxBackground            # встроенный узел — фон 1:1 из механики оригинала
│   └── ParallaxLayer/Sprite2D
├── Terrain (Node2D)              # см. §3
├── Ships (Node2D)                # контейнер спавна кораблей
├── Projectiles (Node2D)          # контейнер снарядов
├── Bases (Node2D)                # Area2D-базы (ремонт/смена оружия/победа)
├── Camera2D                      # limit_* по границам уровня
└── SpawnPoints (Node2D)          # Marker2D
```
- Параллакс-фон оригинала — ровно то, для чего существует `ParallaxBackground`.
- Базы: `Area2D` + `CollisionPolygon2D`. Позиции берутся из палитровых индексов
  32–47 при загрузке уровня (сегментируем связные области нужных индексов), но сами
  зоны — штатные `Area2D`, а не ручные проверки.

> **Реальность на сейчас (devlog §22.2):** `Ships`/`Projectiles`/`SpawnPoints`
> НЕ заведены — `Level._ships: Array[Ship]` уже даёт прямой доступ обоим
> потребителям (HUD, камера), а контейнер без `Bases` (которых тоже пока нет)
> был бы половинчатым шагом без пользы. `SpawnPoints`/честные ARENA.LEV-точки
> заменены на случайный спавн с разнесением (`MatchManager.pick_spawns`).
> `ParallaxBackground`/`Bases` — оба ждут своего шага (§6, шаг 7 и далее).

### 2.3 `ship.tscn` — **`RigidBody2D`**
```
Ship (RigidBody2D)
├── CollisionShape2D (CircleShape2D)
├── Sprite2D                      # rotation = aim_angle
├── Muzzle (Marker2D)
├── Thrust (GPUParticles2D)
├── EngineSfx (AudioStreamPlayer2D)
└── PickupArea (Area2D)           # десантники в одиночной игре
```

**Почему `RigidBody2D`, а не `CharacterBody2D`:** параметры оригинала ложатся на его
свойства один в один, без единой строки собственной физики:

| Оригинал (Options/Rules) | Свойство Godot |
|---|---|
| Gravity | `gravity_scale` (× `ProjectSettings.physics/2d/default_gravity`) |
| Air resistance | `linear_damp` |
| Масса корабля (стат `.SHP`) | `mass` |
| Тяга | `apply_central_force()` |
| Удар о рельеф | `contact_monitor` + `max_contacts_reported`, `body_entered` |

Единственная тонкость: в Wings корабль поворачивается **с фиксированной скоростью
по кнопке**, а не крутящим моментом. Решение без борьбы с солвером —
`lock_rotation = true` и собственная переменная `aim_angle`. Коллайдер круглый
(корабль 15×15 → круг), поэтому поворот тела на физику вообще не влияет:
```gdscript
aim_angle += input.turn * data.turn_rate * delta
$Sprite2D.rotation = aim_angle
if input.thrust:
    apply_central_force(Vector2.UP.rotated(aim_angle) * data.thrust)
```

**Шов под сеть.** Ввод отделён от симуляции: корабль не читает `Input` напрямую,
а получает `ShipInput` (`thrust: bool`, `turn: float`, `fire_primary`, `fire_secondary`)
от провайдера:
- `LocalInput` — читает `InputMap`-экшены `p{N}_thrust` / `p{N}_left` / … (8 игроков × 5
  действий = 40 экшенов, ровно как 8 наборов клавиш в `KEYS.DAT` оригинала).
  Хотсит на одной клавиатуре — это штатный `InputMap`, ничего своего.
- `AIInput` — позже (в оригинале есть Computer-игроки).
- `RemoteInput` — позже; тогда на корабль вешается `MultiplayerSynchronizer`,
  а сервер получает интенты по RPC. Переписывать `Ship` не придётся.

> **Реальность на сейчас (аудит 2026-07-22):** `RemoteInput`/`ShipInputSync`
> уже сделаны (devlog §24) и `NetSync` (`MultiplayerSynchronizer`) уже висит
> в `ship.tscn` (devlog §25) — предсказание сбылось, `Ship` действительно не
> переписывали. Разошлось с диаграммой узлов выше: `Sprite2D` — по факту
> `Visual` (`Polygon2D`, треугольник-плейсхолдер, roadmap.md), `EngineSfx` не
> заведён (звука двигателя пока нет), `PickupArea` не заведён (десантники —
> вне v0.1, `timeline.md`). Ничего из этого не скрыто — все три пункта уже
> отдельно отслежены в `roadmap.md`/`devlog.md`, просто диаграмма узлов сама
> по себе никогда не обновлялась вслед за ними.

### 2.4 Снаряды — `projectile.tscn` (`RigidBody2D`)
```
Projectile (RigidBody2D)
├── CollisionShape2D
├── Sprite2D
└── Lifetime (Timer)              # встроенный таймер вместо ручного счётчика
```
- Гравитация бомб/гранат — `gravity_scale`, бесплатно.
- **Bouncer** (рикошетящий снаряд) — `PhysicsMaterial.bounce`, встроенное свойство.
- **Mine** — `freeze = true` после приземления + `Area2D`-триггер.
- Быстрые пули — `continuous_cd = CCD_MODE_CAST_RAY`, встроенное решение проблемы
  туннелирования; писать свой raycast-марш не нужно.
- Взрыв: `explosion.tscn` (`GPUParticles2D` + `AudioStreamPlayer2D` + вызов
  `Terrain.carve()`), самоудаление по `finished`.

Поведение живёт в скрипте сцены снаряда, числа — в `WeaponData` (§4).

## 3. Разрушаемый рельеф — сравнение и выбор

Требование из механики: **попиксельное** разрушение произвольно нарисованного
битмапа + классы материалов по диапазонам палитры (пустота / вода / огонь / мягкое /
неразрушаемое / взрывчатое).

### Вариант B — `TileMapLayer` со слоями урона → **отклонён**
`TileMapLayer` спроектирован под сетку авторских тайлов. Здесь он не подходит по сути
задачи, а не по производительности:
- источник — свободно нарисованный PNG, а не тайлсет; чтобы положить его в тайлы,
  пришлось бы изобретать автотайл-схему поверх пиксельного арта;
- разрушение стало бы поблочным. Даже тайл 4×4 px убивает силуэт кратера, ради
  которого весь жанр и существует; тайл 1×1 px — это 1200×1200 = 1.44 млн тайлов,
  что абсурдно и медленнее любого битмапа.

### Вариант C — чистая попиксельная физика без физдвижка → **отклонён как основа**
Так делал оригинал (DOS, без физдвижка). В Godot это означало бы отказ от
`RigidBody2D`, `Area2D`, слоёв коллизий, нормалей контакта — то есть ручную
реализацию того, что движок уже даёт. Нормали нужны для Bouncer и для порога
«Ship strength», ими не хочется жертвовать.

### Вариант A — `Image` + `BitMap.opaque_to_polygons()` + чанки → **выбран**

Полностью на встроенных классах: `Image`, `BitMap`, `CollisionPolygon2D`,
`StaticBody2D`, `ImageTexture`, `Sprite2D`.

**Две картинки как источник истины** (обе — `Image`, живут в памяти):
1. `visual_image` (RGBA8) — то, что видно;
2. `class_image` (R8) — класс материала на пиксель, строится один раз при загрузке
   из `visual_image` через `TerrainPalette` (§4.3).

**Чанки.** Рельеф режется на сетку `terrain_chunk.tscn` (ориентир 128×128 px,
параметр). Уровень 1200×1200 → ~100 чанков.
```
Terrain (Node2D)
└── TerrainChunk (StaticBody2D) × N
    ├── Sprite2D (ImageTexture)         # рендер чанка
    └── CollisionPolygon2D × M          # генерируются заново при изменении
```

> ⚠️ **Три поправки, найденные при реализации** (детали и замеры — §8):
> 1. `opaque_to_polygons()` **теряет дырки** — возвращает только внешние контуры.
>    Приходится трассировать ещё и инвертированную маску.
> 2. Контур обязан **замкнуться по краю чанка**, из-за чего у маски пустоты
>    появляются фантомные стены поперёк открытого воздуха. Такие рёбра отбрасываются.
> 3. Из-за (1) и (2) вместо `CollisionPolygon2D` используется
>    `ConcavePolygonShape2D` с явным списком отрезков.

> **Живая физика поверх этого (devlog §49, 2026-07-28).** `Terrain` выше
> по-прежнему единственный рендер+мост коллизии — не заменён и не удалён. Но с
> §49 источником истины для ДВИЖЕНИЯ материала (что куда осыпалось) стала
> клеточная симуляция `SandSim` (`scripts/sand/sand_sim.gd`, изначально
> прототип falling-sand): `scripts/level/live_sand.gd` тикает её в
> `_physics_process` и переносит изменившиеся клетки в `Terrain` через новый
> метод `Terrain.write_block(rect, cls, rgba)` (пишет произвольный класс в
> прямоугольник — `carve_circle` умеет только стирать в EMPTY). Обратная
> связь — по сигналу `carved`: дыра из carve переносится в симуляцию, чтобы
> материал над воронкой потерял опору. Оба разрешения разные (рельеф
> попиксельный, симуляция — клетки `cell_px`, сейчас 6): осыпь квантуется по
> сетке клеток, мельче клетки carve не роняет пласт (порог
> `LiveSandSettings.carve_clear_threshold`). Рубильник
> `LiveSandSettings.enabled` возвращает поведение к статичному рельефу.
> Генерация уровня (`scripts/level/sand_level_gen.gd`) теперь тоже строится на
> `SandSim` (была на процедурном шуме `TestLevelGen`) и берёт числа формы
> уровня из `LevelGenRules` (§4) вместо констант в коде.

**Цикл разрушения:**
```
carve(center, radius, power)
  └─ для пикселей в радиусе: класс из class_image
       INDESTRUCTIBLE -> пропустить
       SOFT           -> радиус × коэффициент
       EXPLOSIVE      -> в очередь цепной детонации
       иначе          -> class_image = EMPTY, visual_image = прозрачный
  └─ пометить задетые чанки dirty (обычно 1–4)
  └─ в конце кадра для каждого dirty-чанка:
       ImageTexture.update(sub_image)                      # рендер
       BitMap.create_from_image_alpha(solid_mask_sub)      # маска твёрдого
       BitMap.opaque_to_polygons(rect, epsilon)            # C++, встроенное
       пересобрать CollisionPolygon2D чанка
```
Перегенерация ограничена задетыми чанками, а не всем уровнем, и делается один раз за
кадр (батч через `set_deferred` / очередь dirty), а не на каждый пиксель.

**Настройки производительности:**
- `epsilon` в `opaque_to_polygons` — упрощение контура; убирает пилу пиксельных краёв.
- Маска коллизий строится в 1/2 разрешения рельефа: полигонов вдвое меньше, разница
  визуально незаметна (мы и так рисуем рельеф крупнее оригинала).
- Если dirty-чанков за кадр много (Nuke), обработка размазывается по кадрам очередью.

**[КАСТОМ] Попиксельный запрос материала для нетвёрдых зон.**
Вода, течения, огонь, снег, пузыри — не коллизия, а свойство точки пространства,
причём вода в оригинале ещё и течёт. Строить на них `Area2D`-полигоны и
перегенерировать их каждый кадр — дороже и хуже, чем `class_image.get_pixelv(pos)`,
то есть O(1) обращение встроенным методом `Image`. Отдельного узла под «карту
материалов» в Godot нет, так что это не замена встроенной системы, а её штатное
использование. Твёрдость при этом остаётся на физдвижке.

## 5. Autoload

**Один autoload: `GameRules`** (`autoload/game_rules.gd`).

Хранит настраиваемые правила матча — те самые пункты меню Options оригинала,
которым в движке нет места и которые нужны глобально и в рантайме. Физические
поля — МНОЖИТЕЛИ с нейтральным умолчанием 1.0 (без настроек — как будто autoload
нет). **Реализовано**, точная раскладка «какое поле где применяется» — в
`notes/devlog.md` §17; здесь — суть:
```gdscript
extends Node
# Физика: множители поверх ShipData/ProjectSettings, 1.0 = «как задано»
var gravity_scale: float = 1.0         # -> RigidBody2D.gravity_scale (× default_gravity)
var air_resistance_scale: float = 1.0  # -> × ShipData.linear_damp
var ship_strength: float = 1.0         # -> делитель ВСЕГО входящего урона (Ship.take_damage)
var reload_time_scale: float = 1.0     # -> × WeaponData.reload_time (кулдаун)
# Матч — читает MatchManager (devlog §22)
var kills_per_level: int = 10
# Рельеф — читает level.gd (devlog §49): 0 = разыграть seed заново при заходе
# в уровень, иначе взять заданный; level_seed_used — что реально выпало
var level_seed: int = 0
var level_seed_used: int = 0
# Детали визуала (флаги на будущее)
var parallax_enabled: bool = true
```
> Изменения против первоначального наброска: `air_resistance` стал множителем
> `air_resistance_scale` (а не абсолютным linear_damp); `ship_strength` теперь
> делит урон, а не множит `crash_tolerance` (то поле удалено — урон от
> столкновения переехал на пороги по скорости в `TerrainPalette`, devlog §14);
> `load_time_scale`→`reload_time_scale`. Поля `starting_weapon`, `water_flow_speed`,
> `snow_enabled` отложены до соответствующих механик.

**Что НЕ кладём в autoload** (для этого есть штатные места):
- Базовая гравитация и демпфирование — `ProjectSettings`:
  `physics/2d/default_gravity`, `physics/2d/default_linear_damp`.
  `GameRules` держит только игровой множитель поверх них.
- Слои коллизий — именованные слои в `ProjectSettings`, а не константы в синглтоне.
- Статы кораблей/оружия — `.tres` (§4), не глобальные словари.
- Состояние матча — узел `MatchManager`, у него жизненный цикл матча.
- Глобальная шина сигналов — **не заводим**. Доступ к рельефу из снаряда — через
  группу: `get_tree().get_first_node_in_group("terrain")`, кэшируется в `_ready()`.
  Группы — встроенный механизм, отдельный синглтон тут лишний.

## 8. Экран и разрешение (решение, 2026-07-22)

Цель — одно и то же окно адекватно выглядит и на Steam Deck (1280×800,
16:10), и на обычном Full HD мониторе (1920×1080, 16:9), и на Retina Mac
разработчика (не целевая платформа, но там ведётся разработка) — без
отдельной вёрстки под каждый вариант.

**Базовое разрешение — `window/size/viewport_width/height = 1280×800`**
(Steam Deck, основная цель по CLAUDE.md: «сначала полностью рабочая версия
под Steam Deck»). Это не «на сколько пикселей рисуем» в смысле пиксель-арта
(проект сознательно HD/векторный, см. CLAUDE.md) — это только опорный размер
для раскладки HUD/UI и для расчёта, сколько докладывать/урезать при другом
аспекте экрана.

**`window/stretch/mode="canvas_items"` + `window/stretch/aspect="expand"`**
(было выставлено раньше сессии, проверено по офиц. доке 4.7, не по памяти —
`multiple_resolutions.html`): `expand` при несовпадении аспекта окна с
базовым НЕ добавляет чёрные полосы (как `keep`) и не тянет картинку с
искажением (как `ignore`) — вместо этого расширяет видимую область в
недостающем измерении. Ровно то, что нужно этой игре: `Level._update_camera()`
уже считает зум камеры от РЕАЛЬНОГО `get_viewport_rect().size`
(`level.gd:189-196`), то есть геймплейный код уже готов к «на широком экране
видно чуть больше поля боя», а не жёстко завязан на один аспект.

**`window/size/mode=2` (`Window.MODE_MAXIMIZED`)** — окно при запуске сразу
занимает весь текущий экран (а не маленькое окно 1280×800 в углу 4K-монитора
разработчика), но остаётся ОКНОМ (не эксклюзивный fullscreen) — на этапе
активной разработки удобнее держать рамку/возможность Cmd+Tab, чем угонять
экран целиком. Реальный `MODE_EXCLUSIVE_FULLSCREEN` — рекомендация той же
доки для готовой игры (без артефакта в 1px внизу экрана, который даёт обычный
`MODE_FULLSCREEN`) — переключить перед экспортом на Steam Deck, не раньше:
там за полноэкранный режим и так отвечает Gamescope, а во время разработки
эксклюзивный fullscreen только мешал бы (не даёт быстро выйти в другое окно).

Значения enum (`WINDOWED=0`, `MINIMIZED=1`, `MAXIMIZED=2`, `FULLSCREEN=3`,
`EXCLUSIVE_FULLSCREEN=4`) и то, что все три поля (`viewport_width/height`,
`mode`, `stretch/*`) действительно читаются движком — проверено не «на
глаз», а прогоном `ProjectSettings.get_setting(...)` в headless-скрипте
после правки `project.godot` (значения совпали).

## Сеть: модель синхронизации (решение, 2026-07-22)

Решение по сетевому PvP — ключевой цели проекта (поставить из Steam, играть с
другом). Принято после сверки с офиц. доками Godot 4.7 (не по памяти — это
нишевый слой, CLAUDE.md требует проверки). Держим строго на «методичке Godot»,
без своего транспорта.

**Итоговая раскладка:**

| Слой | Решение |
|---|---|
| API | **High-Level** (`@rpc`, `MultiplayerSynchronizer`, `MultiplayerSpawner`) |
| Транспорт | **UDP через `ENetMultiplayerPeer`** (в ядре), **не TCP** |
| Топология | **listen-server**: хост = один из игроков, не выделенный сервер |
| Authority | **host-authoritative** по миру (весь ввод клиента — недоверенный) |
| Carve рельефа | **событие** (reliable_ordered `@rpc`) → клиенты replay `carve()` |
| Корабль/счёт | `MultiplayerSynchronizer` / RPC (простые поля) |
| Вода (потом) | host симулирует → редкие грубые снапшоты + локальный предиктор |
| Steam | `SteamMultiplayerPeer` (аддон GodotSteam) позже, **за тем же интерфейсом** |

### Почему не TCP

В High-Level API транспорт не выбирается напрямую — он следует из реализации
`MultiplayerPeer`. ENet — это UDP с **попакетной** надёжностью: `@rpc` задаёт
`transfer_mode` на каждый вызов. Позиция корабля → `unreliable` (потерян пакет —
не беда, следующий через 1/60с свежее), carve/счёт/спавн → `reliable`. TCP
форсирует надёжность+порядок на весь поток плюс буферизация Nagle → лишняя
задержка везде. ENet даёт и низкую задержку UDP, и надёжность TCP там, где нужно.

### Authority vs Transmission — почему «A против B» было ложной дилеммой

Два независимых понятия: *кто решает* (authority) и *как это доезжает*
(transmission). Разбор развилки при проектировании:

- **Чистый детерминированный replay (peer-симметричный)** отклонён как
  архитектура на всю игру по двум причинам: (1) физика `RigidBody2D`/Jolt **не
  гарантированно детерминирована между машинами** — тот же ввод даёт чуть разное
  интегрирование, корабли расходятся, ещё до всякой воды; (2) вода — клеточный
  автомат, малейшее расхождение в кадре растёт каскадом, держать его
  детерминированным между машинами — исследовательский проект, не для соло на
  8 недель.
- **Полный diff (слать изменившиеся пиксели/клетки)** отклонён как способ
  передачи: для воды это тысячи клеток × 60 кадров = смерть канала.

Синтез: **host-authoritative backbone** (единый источник истины) + **передача,
подобранная под каждую подсистему**. Carve при этом передаётся событием и
проигрывается локально — это выглядит как «детерминированный replay», но
безопасно, потому что `carve()` — чистая пиксельная геометрия (тот же
центр/радиус/power по тому же рельефу = тот же результат), а не float-интегрирование
физики. Порядок наложения перекрывающихся carve гарантирует reliable_ordered.
Единственный RNG в carve — в **обломках**, а они декоративны (на коллизию рельефа
не влияют), поэтому остаются локальными у клиента и совпадать не обязаны.
Страховка от дрейфа: хост изредка шлёт контрольную сумму рельефа, полный ресинк —
только при расхождении.

### Почему `MultiplayerSynchronizer` не синхронизирует рельеф

Подтверждено докой 4.7: `MultiplayerSynchronizer` **не поддерживает Object/Resource**
(«Synchronization is not supported for Object type properties, like Resource»).
`Image`/`BitMap` рельефа 1200×1200 через него не прогнать — отсюда и решение
гнать carve **событиями**, а не состоянием. Простые поля корабля (`Vector2`,
`float`, `int`) и счёт синхронизатор тянет штатно.

### Шов уже заложен

Ввод корабля отвязан от источника (`ShipInput` → `LocalInput`/`AIInput`/
**`RemoteInput`**, §2.3) — сеть добавляется провайдером `RemoteInput` + RPC-интенты,
`Ship` переписывать не нужно. `MultiplayerPeer` — тоже шов: прототип на
`ENetMultiplayerPeer` (localhost/LAN, ноль зависимостей), Steam-пир подключается
позже сменой одной реализации пира, RPC-код игры не меняется. Точка входа —
`scripts/net/network_manager.gd` (host/join, прогресс — devlog).

### Осознанно НЕ в этом заходе

Публичный матчмейкинг/NAT-punchthrough (для игры с конкретным другом достаточно
LAN/приглашения через Steam), выделенный сервер, откат/предсказание ввода
(client-side prediction/rollback) — для 2 игроков по listen-server пока не нужны,
добавляются поверх, если понадобятся.

Ссылка: [godotsteam.com/tutorials/multiplayer_peer](https://godotsteam.com/tutorials/multiplayer_peer/)
(официальный туториал GodotSteam; прямой WebFetch страницы вернул 403 — сверено
через поиск и независимые зеркала/обзоры, не додумано по памяти).

Ключевое из доки, важное для нашей архитектуры:
- `SteamMultiplayerPeer` реализует ТОТ ЖЕ `MultiplayerPeer`, что и
  `ENetMultiplayerPeer` — подтверждает решение выше ("шов уже заложен",
  RPC-код игры не меняется при смене пира).
- Подключение — по **Steam ID**, не по IP. Практически всегда через **Steam
  Lobby** (`create_host(0)` на хосте, `create_client(server_steam_id, 0)` на
  клиенте) — Steam сам решает NAT-punchthrough, отдельный relay/матчмейкинг
  писать не нужно (закрывает пункт "осознанно не делаем" выше, когда дойдём).
  Раньше это был отдельный аддон поверх GodotSteam, сейчас функциональность
  влита в основную ветку GodotSteam 4.x — ставить отдельно не придётся.
- **Для тестирования Steam-сети НЕ нужен свой опубликованный App ID.** Valve
  специально держит публичный тестовый App ID `480` ("Spacewar") — с ним можно
  проверять Steam-фичи (лобби, P2P-сеть) без своего аккаунта разработчика и
  без публикации в Steam. Нужно: запущенный клиент Steam на обеих машинах +
  минимум два **не ограниченных** (unrestricted, т.е. не полностью free/новых)
  Steam-аккаунта.

**Прямой вывод под текущий вопрос заказчика** ("можно ли уже выложить в Steam,
чтобы проверить сеть с другом"): не нужно ни сейчас, ни даже когда дойдём до
Steam-пира. Сейчас сеть — `ENetMultiplayerPeer` (не Steam вообще), тестируется
прямым IP/LAN без всякого Steam. А когда добавим Steam-пир — тестировать его
тоже можно будет через App ID 480, без публикации игры.
