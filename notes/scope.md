## Подход к контенту
Оригинал (числа, характеристики, поведение) — как база.
Правки под свой вкус — по ходу тестирования, не обязательно
1:1. Не самоцель точить лором, самоцель — чтобы летать было
приятно.

## Какой уровень взять за основу
Импорт оригинального `.LEV` не входит в v0.1 (архитектурное решение:
свои PNG, импортёр `.LEV` — не сейчас). Значит уровень оригинала — это
**визуальный/компоновочный ориентир** для ручного/генерируемого
`visual.png` + `mask.png`, а не файл для бинарного импорта.

**Рекомендация: ARENA.LEV.** Причины:
- Название прямо указывает на открытое пространство для боя — то, что
  нужно по цели «показательный по механике, не обучающий»;
- размер оригинала 400×400 → при `TERRAIN_SCALE` ×3 (architecture.md,
  шапка) это ровно **1200×1200** — тот самый размер, на котором уже
  откалиброван весь Terrain-бенчмарк (`chunk_size=128`,
  `collision_downscale=2`, `polygon_epsilon=0.5`, architecture.md §8.2–8.3).
  Подобранные параметры переносятся на реальный уровень v0.1 без пересчёта;
- есть параллакс-фон в оригинале (не все уровни его имеют — GROUND и WAR
  без фона), пригодится, когда дойдём до фона по `architecture.md` §9,
  даже если в v0.1 фон не подключаем;
- средний по сложности рельефа (96 679 байт исходного `.LEV`) — не
  тривиальный (как пустые GROUND-подобные), но и не самый тяжёлый
  (LAVACAVE 309 КБ) для первого прохода.

## Технический принцип
Максимально использовать встроенные системы и узлы Godot вместо
написания своих решений с нуля. Кастомный код — только там, где
у Godot действительно нет готового инструмента под задачу. Полный
реестр решений с обоснованием — `architecture.md` §7 (сводная таблица)
и разбор по каждому узлу в §2–§3, §9.

Формулы гравитации/сопротивления воздуха и прочие константы из
оригинала — это входные параметры для нативных Godot-нод (`gravity_scale`,
`linear_damp` у `RigidBody2D`), а не повод писать полностью свой
физический цикл с нуля.

Примеры, где явно предпочтителен нативный Godot:
- Физика: `RigidBody2D` + встроенный физический движок вместо своей
  симуляции гравитации (решено, architecture.md §2.3)
- Столкновения: `Area2D`/`CollisionShape2D` вместо ручной проверки
  пересечений
- Частицы/эффекты: `GPUParticles2D` для взрывов, следов от двигателя
- Анимация: `AnimationPlayer`/`AnimationTree` вместо ручного тайминга
- Аудио: встроенный `AudioStreamPlayer` с шинами (buses) вместо
  своего аудио-менеджера
- Управление ресурсами: `Resource`/`PackedScene` вместо самодельной
  сериализации
- Тайловый рельеф: сравнение с `TileMapLayer` уже сделано и решение
  принято — **не подходит по сути задачи** (свободный битмап, не
  тайлсет; поблочное разрушение убивает силуэт кратера). Взамен —
  `Image` + `BitMap.opaque_to_polygons()` по чанкам, единственный
  кастом — попиксельный запрос материала (вода/огонь/течения), и тот
  дополняет физдвижок, а не заменяет. Полный разбор и три поправки,
  найденные при реализации, — `architecture.md` §3 и §8.1.
