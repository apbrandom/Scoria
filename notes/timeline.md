# План по неделям — 8 недель до Steam-релиза

Цель, ради которой считаем недели: поставить игру из Steam и играть в PvP
с другом. Не полный клон оригинала (31 оружие, 17 уровней, кампания) — фокус
на геймплей/физику/бой, лор и арт вторичны (см. обсуждение приоритетов,
devlog §22 preamble). Дни считаем от 2026-07-20 (день начала проекта).

**Как читать этот файл.** Это не жёсткий контракт по датам — солью-один-раз
план на 8 недель для проекта, где две вещи (сеть, физика материалов —
недели 2–3 и 5) — по сути R&D с неизвестным заранее объёмом работы, тот же
класс риска, что раньше был у Terrain (там тоже был отдельный этап
прототип→бенчмарк, не оценка на глаз). Перепланировать в конце каждой недели
по факту, а не тащить план как есть до конца. Пункты не расписаны на дни —
день/два себе на манёвр внутри недели закладывать нормально.

Раз в неделю, вместе с перепланированием, сверяться с картой модулей
(`architecture.md` §0): не утекла ли связность между направлениями, которые
должны развиваться независимо (Полёт/Боты/Левел-дизайн/Арт) — единственная
пара, которой закладывается тесная связь заранее, это Рельеф и Сеть.

## Неделя 2 — сеть, часть 1: архитектурное решение + прототип

Самый рискованный оставшийся пункт всего плана — сеть не бесплатно ложится
на `RigidBody2D`-физику, и разрушение рельефа обязано быть ОДИНАКОВЫМ у
обоих игроков (иначе один видит проход, другой — стену). Дешевле решить
архитектуру сейчас, чем переделывать код `Ship`/`Terrain`/`Projectile`
постфактум — цена ошибки растёт с каждой написанной поверх фичей.

- [x] Решить модель синхронизации: **host-authoritative**, carve — событием
      (reliable_ordered `@rpc`) + локальный replay, не diff и не peer-симметричный
      детерминизм (чистый replay отклонён: `RigidBody2D`/Jolt не детерминирован
      между машинами, водяной CA хрупок). Зафиксировано в `architecture.md` →
      «Сеть: модель синхронизации» (devlog §23.1).
- [x] Решить модель для корабля/снарядов: `MultiplayerSynchronizer` (простые
      поля) + RPC-интенты через шов `ShipInput`/`RemoteInput` (architecture.md
      §2.3). Решено; реализация `RemoteInput` — ниже.
- [x] Прототип подключения: сервер+клиент по `ENetMultiplayerPeer` видят друг
      друга (localhost). Сделано как `NetworkManager` + headless-тест коннекта
      в одном процессе (~4 кадра до connect, 15 проверок, devlog §23.2–23.3).
- [x] `RemoteInput` + `ShipInputSync`: ввод владельца доезжает хосту по RPC
      (host-authoritative, unreliable_ordered). Проверен путь ВВОДА (devlog §24).
- [ ] Синхронизация СОСТОЯНИЯ корабля хост→клиенты (`MultiplayerSynchronizer`:
      позиция/поворот) + carve по reliable_ordered `@rpc`. **Цель остатка
      недели — не готовая фича, а понять, где больно**, пока это дёшево править.
- [ ] Вплести NetworkManager в поток игры (меню host/join → Level) — сейчас
      сетевые классы живут только в тестах.

## Неделя 5 — физика материалов рельефа (выбрать ОДНО)

Самый амбициозный пункт бэклога: осыпание земли (разрушенный пиксель
скатывается вниз, а не исчезает) и вода (течёт, заполняет пространство) —
оба, по сути, клеточный автомат вроде «падающего песка» (Noita/Powder Toy),
не готовая система Godot. `terrain_materials.md` уже фиксирует: вода —
самая тяжёлая часть техническо (плюс отдельный рендер-слой для
плёнки/дрожания), а осыпание — по сути та же задача плюс мост обратно в
статичный битмап Terrain, когда материал осел.

- [ ] В начале недели — честно оценить, какое из двух реалистичнее за
      оставшееся время, и взять ОДНО, не оба сразу.
- [ ] Тот же процесс, что был у Terrain: прототип → бенчмарк на реальном
      уровне → решение, не наобум (architecture.md §8 — пример такого захода).
- [ ] Таймбокс: если к концу недели прототип не показывает приемлемую
      производительность/ощущение — сознательно отложить, не тонуть.
